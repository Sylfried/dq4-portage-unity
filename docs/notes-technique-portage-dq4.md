# Portage PC de DQ4 (Android) : notes techniques (état au 29/10/2026, soir)

> Copie du 30/10/2026 des notes du dépôt `dq4-pc` (privé). Les passages sur la visionneuse (`fenetre.py`, `ui_menu.py`, `son.py`), sur `outils/ui_il2cpp` et sur `test_faisabilite/` décrivent des fichiers qui sont restés dans `dq4-pc` ; le protocole moteur -> Unity, les paquets et les données Unity valent pour les deux dépôts.

## Architecture du jeu
- Unity 2022.3.62f3 (IL2CPP, ARM64 uniquement) + moteur C++ autonome `libdq4core.so` (2,4 Mo, 6 664 fonctions exportées avec noms conservés).
- Le moteur n'utilise que libc/libstdc++, `liblog` et 3 appels OpenGL (`glBindTexture`, `glGetError`, `glTexSubImage2D`, tous dans `TextureWriter`). Aucun appel de tracé : c'est Unity qui dessine.
- Points d'entrée (C) : `IsLoadNativeCode`, `DevInit(chemin_apk_données, chemin_sauvegarde, langue)`, `MenuPortInit(32, tampon_unity, 129, tampon_natif, 1089)`, `GameInit(input, output, output_float, str)`, `GameUpdate(pad_press, pad_toggle)`, `UnityRenderEvent`, `GetMessageCanvas`.
- `DevInit` reçoit le chemin de l'APK de données : le moteur lit lui-même le ZIP (21 ouvertures de l'APK au démarrage).

## Test de faisabilité (voie A) : RÉUSSI
- `portage_pc/test_faisabilite/` (`lancer_test.bat` + `test_core.py`, archive locale non versionnée ; `dq4_pc/emu_core.py` en est la suite) : chargeur ELF AArch64 maison + Unicorn. 61 constructeurs C++, DevInit, MenuPortInit, GameInit et des centaines de GameUpdate tournent. Validé sous Windows (Python 3.15, pc "pdc") et Linux.
- Vitesse : GameUpdate ~15 ms/image dans l'émulateur.

## Protocole moteur -> Unity (tampons de sortie)
- Deux curseurs globaux (dans la lib : entiers 0x258278, flottants 0x258280). Chaque image : flux d'entiers `[état, paquet, paquet…]` (terminé par -1) et flux de flottants parallèle. Le protocole est **différentiel** (Unity garde l'état : le moteur n'envoie que les changements).
- Découpage fiable des paquets : surveiller les écritures sur le curseur d'entiers (= validation d'un paquet) ; les flottants appartiennent au paquet « ouvert » (UnityGetPacket appelé, pas encore validé), sinon au dernier paquet validé (caméra 10 et chargement 11 : flottants écrits après la validation).
- **Le 1er entier du tampon de sortie est un mot d'état partagé** lu au début de chaque GameUpdate (stocké dans Global+0xd8). Bit0 = fondu en cours (mis par `UnitySetFade`, qui émet aussi un paquet type 9) : **Unity doit le remettre à 0 quand le fondu est fini**, sinon le moteur ne change jamais de partie/carte (cause du blocage initial). Autres bits mis par le moteur : bit2 `PlayerManager::setLock`, bit3 `UnityInitTouchFlag`, bit4 `TownCamera::setLimit`.
- `UnityGetPacket(type)` écrit le type et renvoie le curseur ; `UnitySetPacket(a,b)` ajoute 2 entiers ; `UnitySetPacket(int*)` valide ; `UnityGetFloatPacket(n)` réserve n flottants.
- **Paquets décodés :**
  - 0 = chargement d'une carte Unity : `unity_load_fld(nom, genre)` écrit le chemin de la ressource dans un tampon interne (lib+0x258290), ex. `ev/ev01/out/ev01` (titre), `m/ml/in/mlb1a` (1re ville), `m/ma/…/mak1f1`, `btl/<a>/stage/<b>` (combats) ; suivi d'un paquet 11 (flags + flottant).
  - 9 fondu ; 8 (6 flottants) ; 37/35 sons.
  - 10 caméra : entier = flags (bit0 position, bit1 cible), flottants x,y,z (Unity, y haut). FOV vertical 20° pour les villes (Camera Unity du datapack).
  - 12 `(slot, id)` : crée un sprite de personnage (id -1 = libère) ; la feuille de sprites est la texture Unity `h<id>` (ex. `h106`).
  - 13 mise à jour de sprite : entier 1 = flags | slot (slot sur 11 bits) ; bit11 → 1 flottant (échelle, 0.045 au début), bit12 → 4 flottants (couleur RGBA 0-1, alpha = fondu), bit13 → 3 flottants (position x,y,z monde = valeur/4096, z inversé), bit14 → un entier `pose | direction<<8`. 15 : bit12 → 3 flottants, bit13 → 1 flottant (÷12). 16 = fin d'animation.
  - 21 (slot, id) chargement de modèle (id -1 = libération) ; 22 maillage dynamique ; 31 ModelObject setup/cleanup ; 32 ModelObject::draw ; 28 FieldData::drawBlock ; 14, 18, 19-20 billboards/objets, 24-25 effets, 27-30 cartes/symboles, 34 effet d'écran (sémantique à établir).
- **Feuille de sprites `h<id>`** : cases de 24×32 px, 3 colonnes (pose 0-2) × 8 lignes (direction + variante), dans une texture 128×256. Les textures `m<id>` sont les monstres (combat) ; `m8901` = logo du titre.

## Démarrer le moteur sans Unity
- Singleton `Global` : pointeur à lib+0x23d438. Parties (`Global+0xc0` = actuelle, `+0xee` = id) : 3 = GameStartPart (menu de debug), 0xc = TownPart (le titre « ev01 » est une carte de ville), FieldPart, BattlePart, CasinoPart, BookPart.
- `Global::startTown(this, "nom")` + simulation du fondu (mettre à 0 le bit0 du 1er entier du tampon de sortie avant chaque `GameUpdate`) = change de carte. Nécessite au moins 1-2 `GameUpdate` avant (le curseur d'écriture doit exister).
- **Charger une sauvegarde : `profile::SaveLoad::loadbank(bank)`** (statique ; `bank` 0 = `data1.dat`, 15 360 octets ; le moteur ouvre `<chemin_sauvegarde>data1.dat`, sans « / » intermédiaire avec `/dq/save`). À appeler après quelques `GameUpdate`. Il restaure le groupe et relance la ville (`restartChurch` → `startTown`) ; la sauvegarde n°1 de l'utilisateur se trouve dans une église (carte `mak1f1`).
- `GameManager::resetParty` plante tant qu'aucune ville n'a été initialisée (`GameManager::initialize` est appelé par `TownSystem::initialize`).

## Carte du monde (FieldPart, 30/10/2026)
- Partie `0xe` (`Global+0xee`) ; la ville = `0xc`. On y entre en marchant hors du village (`maout`, porte) ou par `Global::startField()` ; le retour se fait par la porte (paquets `12(slot,-1)` x N + `27(0)` -> partie `0xc`, carte `maout`). À l'arrivée en ville, le héros est posé sur la case de la porte : Haut reste en ville, Gauche/Droite/Bas ressortent aussitôt (comportement du moteur).
- Monde 256x256 cellules de 16 px (CWorldMap : table de 6 octets à FieldData+0x180, largeur +0x198, hauteur +0x19c, tour du monde modulo). Atlas = texture Unity `field` 1024x1024 : tuiles 16x16, id%64 = colonne, ligne comptée depuis le bas, **tuile stockée retournée verticalement** (inverser v dans les UV).
- Paquet 28 = fenêtre de tuiles visible : ints `[x0, y0, colonnes=25, n=1300, tuile...]`, floats `[cam_x_px, cam_y_px]` (la caméra suit le héros).
- Sprites sur la carte : paquet 12 `(slot, 4096 + id)` -> feuille `h<id>` ; paquet 13 avec le drapeau 0x8000 = position (x, y, z en pixels, z = couche 200/180), 0x4000 = pose | direction<<8 ; le paquet 14(idx,1) précède 13.
- Paquet 29 = icônes (villes, châteaux, grottes...) : `FieldData::draw_symbol(idx, genre, x, y)` envoie int = `idx | genre<<8`, floats `[x_gauche_px, y_haut_px, alpha]` (alpha = octet/31) ; `0x8000|idx` = cacher ; `0xC000|idx` = remontrer. Table des symboles du moteur : pointeur à FieldData+0x170, 95 entrées (compteur à +0x1a0) de 10 octets `[0]=drapeau, [1]=genre, [2:4]=id int16, [4:6]=x, [6:8]=y, [8]=largeur, [9]=hauteur` ; position envoyée : `gauche = x-(l>>1)-1`, `haut = y-h` (ancre = bas-centre, comme le héros : le héros démarre exactement sur l'ancre du village, symbole 15, genre 4). Genres 18 (32x16) et 19/20 (`setKekaiSymbol`) : pas dans l'atlas, non dessinés.
- Genre -> case de l'atlas `field` (x, bas, l, h ; image 1024x1024, y du haut vers le bas ; ligne 1 ancrée en bas à y=512, ligne 2 à y=448) : 0 (0,512,48,32) · 1 (96,512,48,32) · 2 (192,512,48,48) · 3 (288,512,41,32) · 4 (384,512,41,32) village · 5 (480,512,25,31) · 6 (544,512,25,31) · 7 (608,512,40,32) · 8 (704,512,24,24) · 9 (768,512,32,32) · 10 (832,512,40,32) · 11 (928,512,24,40) · 12 (0,448,32,46) · 13 (64,448,26,28) · 14 (128,448,41,39) · 15 (224,448,27,42) · 16 (288,448,48,48) · 17 (384,448,40,32). Trouvé en rapprochant les tailles nominales de la table avec les boîtes segmentées de l'atlas (planche contact vérifiée à l'oeil). Les icônes sont stockées **tête en bas** dans l'atlas (comme les tuiles) et dessinées **à plat** sur la carte (le haut de la carte = le bas de l'image), rectangle `[x_gauche, y_haut, l, h]` en pixels, y = 0,02 pour passer devant les tuiles.
- Orientation : la matrice de vue gauche-droite d'Unity regarde vers -z ; sans correction la carte était en miroir (montagnes à gauche) -> miroir en x dans `_camera_champ`. Filtre `GL_NEAREST` sur l'atlas (pixels nets, sinon flou) **avec `net = 0`** dans le shader : le mode « net » (bilinéaire adouci) vise le bord des texels et, en NEAREST, pioche la tuile voisine -> filets clairs entre rangées. `centroid` sur les UV du shader + recul de 0,3 texel : plus de filets non plus avec l'anticrénelage x4.
- **Caméra et sprites de la carte du monde, lus dans le code d'origine (30/10)** : `Field.Init` (D `0xCD1E2C`) crée une caméra **orthographique** (`Rotate(90, 0, 0)` = vue de dessus, near 1, far 400, `orthographicSize = 128 / (largeur / hauteur)`, donc 256 px = 16 tuiles en largeur : en portrait 450 x 800, 28,4 tuiles de haut) ; `Field.SetPosition(x, y)` la place en `(x, 200, -y)` ; `Field.SetScale(s)` multiplie `orthographicSize` et l'échelle des objets flottants. Les valeurs « caméra inclinée, FOV 30, hauteur 19 » étaient des estimations fausses. `Global.CameraInitParams[0]` (mode 0, terrain) : fov 9,5, angleX −47, distance 39,55, near 5, far 100, scaleW 0,0625, `targetCamera` vrai (la ville) ; [1] = combat (48, 0, 0, 0, 39,55, 0,25, 500, 0,0625, yOffset 0,04). `Chara.SetFieldMode` : rotation 90° en X (à plat), `localScale = s_FieldScale` ; `c_FieldScale = 51,84` (= 28,8 x 1,8) sur un maillage de ~0,48 x 0,64 -> héros ~24,9 x 33,2 px (feuille 24 x 32). **Carte entière** : `FieldData+0x188` -> grille `ushort[256 x 256]` (numéro de bloc = `(v - 1) & 0x3ff`), `FieldData+0x180` -> table de 1024 blocs de 6 octets `[?, type, s2, s4]` ; tuile = `s4 + b0` si type 0, `s2 + b2` si type 0x18, `s2 + b1` si type 8, sinon `s2` (`b0, b1, b2` = shorts en `0x275830`, `0x275834`, `0x275838`, décalages d'animation) ; `drawBlock` envoie 25 colonnes x 52 lignes autour de la caméra (`[0x1c0] = cellule x - 8`, `[0x1c4] = cellule y - 14` ; marges -4/+21 et -10/+42).
- La texture `dsdq4wmap01` (256x256) et le TextAsset `dsdq4wmap01m` (196 608 octets = 256x256x3) du datapack sont la mini-carte DS, pas l'atlas.

## Combat (BattlePart, partie 0xd ; 30/10/2026)
- Déclenché par une rencontre sur la carte du monde. Paquet 0 `[256]` charge le décor `btl_<terrain>_<d|e|n>` (ex. `btl_wd_d` forêt de jour, `btl_pl_d` plaine) ; à la fin (fuite/victoire) la partie repasse à 0xe et le moteur renvoie la carte du monde.
- Caméra de combat (**lue dans le code Unity d'origine**, `NativeManager.cmd_camera` D14568 + `SceneCamera.Update` D16180) : paquet 10, flags 5 = position + rotation, flottants `[x, y, z, ax, ay, az]` en degrés. Unity place la caméra en `(x, y, z)` **sans conversion** (monde gauche d'Unity, +x à droite quand on regarde vers +z) avec `eulerAngles = (-ax, -(ay + 180), az)` (mode sans cible : `s_targetCamera` faux). Exemple : `(0, 4,75, -39,8)`, `(-0,7, 180, 0)` -> regarde vers +z, très légèrement vers le bas. Projection : `Global.InitCamera(1)` (appelé par `cmd_fld_load` quand l'entier du paquet 0 a le bit 8 : `0x100` = combat) applique `CameraInitParams[1]` : champ de vision nominal **48**, near 0,25, far 500, `yOffset` 0,04 ; `SceneCamera.Update` multiplie le champ par **4/3** et construit la matrice avec `Matrix4x4.Perspective(fov, 1/aspect, ...)` puis **échange** les éléments m00/m11 -> le champ obtenu (64°) est **horizontal** pour une vue 4/3 (vertical 50,25°) ; `s_scaleW` (0,0625) multiplie toute la matrice (sans effet) et `yOffset` décale l'image de 0,04 en NDC vers le haut. Le paquet 11 (`cmd_camera_sub` : bits near, far, fov borné à 78...) peut changer ces valeurs (pas vu en combat). Décor : `cmd_fld_load` en mode combat appelle `FldObject.SetDispScale(6, 6, 6)` : **la racine du décor est agrandie ×6** autour de l'origine (`FldObject.Update` -> `localScale`), sans autre décalage ni rotation (les rotations/décalages « au jugé » de +27 en z, +3,5625 en y et 180° des premières versions n'existaient pas : ils compensaient l'échelle et la caméra inversées).
- Paquet 21 `(emplacement, id)` (`DSSAObject::send_unity_load`) : id de modèle -> texture Unity `m<id sur 3 chiffres>` (256x256, feuille de pièces 16x16 du monstre) ; id -1 = libère.
- Paquet 22 = maillage dynamique du monstre (`NativeManager.cmd_mesh` D13F74), renvoyé à chaque image : ints `[emplacement, nb_sommets, ceil(nb/4) entiers de couleur (1 octet par quad, alpha ; rgb blanc), indices de triangles (0,3,2,0,2,1 par quad)...]`, flottants `[x, y, z (position du monstre), (u, v, x, y, z) * nb_sommets]` ; `v_texture = 1 + v` (v <= 0, texture en répétition). **Orientation** : chaque `MeshChara` est « billboardé » à chaque image (`NativeManager.Update` -> `MeshChara.SetBillboard`) avec la rotation `caméra × s_yReverse` où `s_yReverse = Euler(0, 180, 0)` (`SceneCamera.SystemInit`) : sommet local `(x, y, z)` -> monde `pos + R_caméra·(-x, y, -z)`. **Rendu** : shaders `Custom/DssaMonster0` (file de rendu Transparent+150) / `DssaMonster1` (+200), lus dans le datapack : **fusion alpha (SrcAlpha, OneMinusSrcAlpha), `ZWrite Off`, `ZTest LEqual`, `Cull Off`**, fragment = `texture × couleur de sommet × _Color`. Donc les parties d'un monstre sont dessinées **dans l'ordre des paquets (ordre des triangles)**, sans aucun tri en z (le z local minuscule ne sert à rien) ; entre monstres Unity trie par file de rendu puis du plus loin au plus proche. Un monstre = ~10 à 19 quads ; le **nombre de sommets change d'une image à l'autre** (poses ; ex. ver 68/72, rat 36/40/48). **Piège :** recréer la liste de sommets quand le nombre de sommets change corrompt les autres monstres (glitchs) -> listes de capacité fixe.
- Autres paquets de maillage (même fonction `NativeManager`) : 21 `(emplacement, id)` crée le `MeshChara` (shader 1 = DssaMonster0, ou 3 = DssaCharaTransparent si id > 999 ; couleur blanche) ; 23 `(emplacement, visible)` ; 24 `emplacement | shader << 8` (0 DssaChara : ZWrite, +100 ; 1 DssaMonster0 ; 2 DssaMonster1 ; 3 DssaCharaTransparent : ZTest Always, Overlay-150) ; 25 `emplacement` + flottants `r, g, b` (`Material.color`) ; 26 flottants `u, v` + `emplacement` (`Material.SetTextureOffset`). Décodés dans `Etat.mesh_etat`.
- Les fenêtres du combat (liste Combattre/Fuir, commandes Attaquer/Magie/Objets/Défense, équipe) passent par les mêmes ports de menu que sur le terrain. Étiquettes/valeurs sur plusieurs lignes (`PV\nPM\nNv.`) : une ligne par statistique.
- **Découvertes de la piste 3 (30/10/2026, pont Unity)** :
  - **Mort d'un monstre** : aucun paquet ne la signale (ni 21 `-1`, ni 23, 25, 26) ; le moteur **cesse simplement d'envoyer le paquet 22** du monstre vaincu (les vivants en reçoivent à chaque image, avec au plus 3 images d'interruption pendant les coups). Le dernier maillage reste donc affiché ; les deux emplacements ne sont libérés (21 `-1`) qu'à la fin du combat. Le pont Unity compte les images sans paquet 22 (8 images = vaincu) et fait disparaître le monstre en fondu de 12 images. Piste à vérifier : un monstre endormi pourrait aussi cesser d'être mis à jour.
  - **Fenêtre de message : le canevas du texte est circulaire** (512 x 256 d'après l'appel de la visionneuse ; **corrigé le 30/10 soir par la piste 1 : Unity crée `Texture2D(512, 512)`, la visionneuse crée désormais le canevas en 512 x 512 (`CANEVAS_H`), il boucle donc modulo 512, voir la section Interface d'origine : affichage**). Le défilement `defil` (`obj_msg + 0x4a`) augmente d'une ligne à chaque message (plus de 800 sur un combat de 4 coups) et dépasse la hauteur du canevas ; il faut lire les lignes `[defil + 3, defil + 3 + lignes * lh)` **modulo 256**. Sans le bouclage (`Moteur.lire_message` actuel : `a[top:top + h]`), le texte devient vide dès que le défilement dépasse ~170 : mesuré sur un combat, 428 images sur 679 avec une fenêtre vide, contre 68 (les pauses entre deux messages) avec le bouclage. À corriger dans `moteur.py` (copie corrigée : `Pont.lire_message` dans `dq4_pc/pont.py`).
  - **Effets de coup** : le coup de Ragnar crée un emplacement temporaire (2) avec le modèle **5303** (texture `m5303`, 64 x 64 : traits de lame et étincelles), shader 3, ~10 images, opacité par quad variable. Les sons (paquet 35) sont envoyés avec : 412 = coup, 402 = message de dégâts, 409 = fanfare de victoire.
  - Points de vie : introuvables en mémoire comme entiers de 16 ou 32 bits (recherche de valeurs baissant de 11 puis 8 aux coups), probablement codés.
- **Mode immédiat (visionneuse, 30/10/2026)** : un maillage n'est dessiné que les images où le moteur a envoyé son paquet 22 (`Etat.maillages_vus`, remis à zéro à chaque image). Clignotement d'un monstre touché = le moteur saute 2 images sur 4 ; mort = le paquet ne revient plus. Avant, la visionneuse gardait le dernier maillage : monstre « figé » après un coup, pas de clignotement.
- **Fondu d'écran (paquet 9 = `NativeManager.cmd_fade`, D14C70)** : entier `v` ; durée en images = `v & 0x7ff` ; bit 12 = sortie (`Fade.SetFadeOutBlack`/`White`/`Color`), sinon `Fade.SetFadeIn` ; bit 11 = couleur donnée par 3 flottants r, g, b ; bit 13 = blanc (sinon noir) ; bit 14 = plan devant l'interface (`SetFadePriority`). Valeurs vues : `4126` (0x101E : sortie noire en 30 images) puis `30` (entrée en 30 images). `Fade.FadePlane.Update` (CD0618) : une fois par image, `n -= 1`, opacité += pas, opacité visée à la fin. L'entrée repart de l'opacité 1. Le moteur ne s'arrête pas sur la fin du fondu (Unity ne lui renvoie que la caméra et la fin des animations, `NativeManager.Update` D15758) : il change de scène 3 images après la sortie et lance aussitôt l'entrée, donc on voit surtout une entrée en fondu à chaque changement de scène (début et fin de combat, entrée dans une ville...). Rejoué dans `Etat._fondu` / `tick_fondu`, dessiné derrière l'interface (`_dessiner_fondu`).
- Paquet 34 = `cmd_screen_effect` (D15024) -> `Capture.ScreenEffect(type, null)` : vu une fois `(34, [4])` à la fin d'un combat (effet sur capture d'écran, non rejoué). Paquets 35/36/37 : 35 = bruitage (`cmd_se_play`, ids 300, 307, 309...), 37 = musique (`cmd_bgm` : 1, 5, 14, 21, 30...).

## Données Unity (datapack.unity3d)
- Se lit avec UnityPy 1.25.4 : 12 267 GameObject, 10 627 Mesh, 4 619 Texture2D, 11 645 Material, 700 TextAsset (.map), 46 AnimationClip, 38 Camera.
- **Une carte = un GameObject racine `<nom>.fld`** (`mlb1a.fld`, `mak1f1.fld`, `ev01.fld`…) avec des enfants : décor principal `000_<nom>` (plusieurs sous-maillages = matériaux, textures `*.tim`), et des petits quads pour les accessoires (coffre, tonneau, pot, porte, torche…) dont les positions sont posées par le moteur. `<nom>.map` (TextAsset, en-tête « FHDR ») décrit objets et collisions.
- Lecture Mesh : `MeshHandler(m).process()` (sommets, UV0, couleurs, triangles par sous-maillage). Textures : `Texture2D.image` ; UV : v inversé.
- Lien id de modèle 3D (8900…, titre) -> objet Unity : non résolu.

## Côté Unity d'origine : inventaire (30/10/2026)
- `base.apk` : `assets/bin/Data/data.unity3d` (8,5 Mo) = **une scène minimale** (`Main Camera`, `New Text`), 8 matériaux (Sprites-Default, Button, Menu, SE-GARRIR, polices), 45 shaders, 491 MonoScripts dont **51 classes de jeu** (`Assembly-CSharp`) : `Boot, MainLoop, Global, NativeCall, NativeManager, Field, FldObject, FbxObject, Chara, MeshChara, MeshCapture, BillboardObject, SceneCamera, BackColor, Fade, FrameMaker, MenuParts, MenuMessage, MenuPortSystem, MenuPortItem, MenuPortItemTable, HoppingNumber, Riseup, Sound, Staffroll, TouchPad, InputName, Capture, Cleaner, DebugViewer...`. `Managed/Metadata/global-metadata.dat` (5 Mo) + `lib/arm64-v8a/libil2cpp.so` (30 Mo, dans `split_config.arm64_v8a.apk`).
- **Pas de prefabs d'interface ni de scènes dans les données** : fenêtres, menus, caméras (champ de vision, déplacements) et placement des scènes sont du code C# compilé (IL2CPP) + des paramètres envoyés par le moteur. Les valeurs « estimées » de la visionneuse (champ de vision de combat, positions des fenêtres) sont donc à lire dans ce code (outil `outils/dump_il2cpp.bat` : liste des classes, champs, méthodes avec leurs adresses ; puis désassemblage ciblé avec capstone).

## Interface d'origine : affichage, fenêtre de message, plaques (30/10/2026, issue #56)
- **Une fenêtre `MenuPortItem` n'est vue que tant que le moteur le demande** (`MenuPortItem.Update`, 0xD0670C) : `NoticeReceive` cmd 5 = `m_bDrawRequest`, cmd 6 = saisie permise, cmd 7 = arrêt (`m_objectActive = false`, parties désactivées), cmd 8 `[1]` = ignorer les demandes (toujours vue, ex. bandeau des personnages). À chaque image : si non ignoré, `m_bDraw = m_bDrawRequest` puis `SetVisible(m_bDraw)` ; la demande est remise à faux. ## Son : conteneur AKB, paquets 35/36/37 (30/10/2026, issue #17 / #42)
- **Fichiers** : `assets/sound/BGM01..BGM51.akb` (51 musiques) et `SE0300..SE1170.akb` (634 bruitages) dans l'APK de données (`split_UnityDataAssetPack.apk`). Lus par `libsdlib_android.so` (`akbMaterial*`), joués côté Unity par `Sound.PlayBGM / StopBGM / PlaySE / StopSE`.
- **En-tête AKB** : `0x00` `AKB ` ; `0x04` u16 version ; `0x06` u16 taille d'en-tête ; `0x08` u32 taille du fichier ; `0x0c` u8 codec (**2 = MS-ADPCM** pour les bruitages, **5 = Ogg Vorbis** pour les musiques) ; `0x0d` u8 canaux ; `0x0e` u16 fréquence ; `0x10` u32 nombre d'échantillons ; `0x14` u32 début de boucle ; `0x18` u32 fin de boucle (0 = pas de boucle) ; `0x20` float volume propre au fichier (0,65 à 0,9 pour les musiques). Bloc d'extra à `0xc0` : u16 `0`, u16 taille de bloc ADPCM (`0xc2` : 22 mono / 44 stéréo = 32 échantillons par bloc), u32 échantillons, u32 début de boucle. Données à `0xcc` : Ogg complet (codec 5) ou 4 octets puis blocs MS-ADPCM (codec 2).
- **MS-ADPCM** : coefficients standard de Microsoft (256/0, 512/-256, 0/0, 192/64, 240/0, 460/-208, 392/-232), en-tête de bloc = indice de prédiction, delta, échantillon 1, échantillon 2 (regroupés par canal), sortie dans l'ordre échantillon 2, échantillon 1, puis les quartets (poids fort d'abord ; en stéréo ils alternent gauche / droite). **La prédiction `(a*c1 + z*c2) >> 8` est une division entière vers zéro** (pas un décalage arithmétique) : c'était la seule différence avec ffmpeg. Vérifié : 53 bruitages sur 53 identiques à `ffmpeg -acodec adpcm_ms` (écart 0). Musiques : `soundfile` (libsndfile) et ffmpeg donnent le même signal (écart <= 1).
- **Paquets** : **35 `[id]`** = `PlaySE(id)` (`SE%04d`) ; **36 `[id]`** = `StopSE` ; **37 `[id]`** = `PlayBGM` (`BGM%02d`), une valeur >= 4096 (ex. 16392 = 0x4008) = `StopBGM`. Vus : musique 14 = village de départ, 5 = carte du monde, 30 = combat, 23 après la victoire (précédée d'un arrêt 16392), puis retour à 14 ; bruitages 307 = pas, 300 = valider / page de message suivante (envoyé par le moteur), 400 à 415 / 804 / 805 = combat, 409 = fanfare, 306 / 609 = fin de combat.
- **Bouton de menu** : le bruitage 300 de l'appui sur un bouton est joué par Unity (`MenuPortItem.Update`), pas par le moteur : le moteur ne l'envoie que pour la validation d'un message. La visionneuse le joue à l'appui d'un bouton (souris) et à la validation / annulation au clavier. Déplacer le curseur ne produit aucun bruitage.
- Non étudié : `snd_vol.dat` (table de volumes), fondus entre musiques (`PlayBGM` côté Unity), bruitages 3D / positionnels.
